# API failures and contract mismatches

Recorded from the final local run on 2026-11-28. The assertions and generated expected statuses were kept unchanged. The run exercised 284 generated EP/BVA cases, 80 decision-table combinations, 9 state-transition cases, and 5 additional workflow/role/repeat-request tests: **341 passed, 37 failed, 0 errors** in 401.97 seconds. The raw pytest transcript is in [api-pytest-run.txt](evidence/api-pytest-run.txt).

The tests read the shared `Reservation` back after every rejected request and after every successful create or state change. The rejection read-backs stayed unchanged for the failed rejection cases. The X-Requested-With action cases were accepted by the app and the read-back showed the reservation changed from pending to accepted. Both duplicate-create checks read back the successful records and confirmed distinct records.

## Findings

| Case(s) | Request and actual response | Expected behaviour and rule | Assessment |
|---|---|---|---|
| API-0002–0006 | `GET /rooms/api/rooms//timeline` (also `None`, non-integer, and negative `room_id` paths), with `X-Requested-With: XMLHttpRequest` -> **404**, body `{}`. | A malformed/nonexistent room ID should be rejected with 404; the OpenAPI NotFound response also declares an `ErrorEnvelope`. The room ID must resolve to a non-deleted room (OpenAPI `RoomId`; route in `indico/modules/rb/blueprint.py:50-51`). | Status and room rule are met. The unmatched Flask route returns an empty body rather than the declared error envelope. Response-schema mismatch. |
| API-0231–0235 | `GET /rooms/api/bookings/` (also `None`, non-integer, and negative IDs) -> **404**, body `{}`. | The booking ID must resolve to a reservation whose room is not deleted; 404 is expected, with the OpenAPI NotFound error shape (`indico/modules/rb/controllers/backend/bookings.py:240-250`; `openapi/openapi.yaml`, `NotFound`). | Status and record rule are met; error body does not match the declared response schema. |
| API-0244–0248 | `POST /rooms/api/bookings//approve` (also missing, `None`, non-integer, and negative IDs), JSON `{"reason":"valid"}` -> **405**, JSON error title `Method Not Allowed`. | The generated cases expect 404 for an invalid booking ID; the ID must resolve before an action can apply (BR2/BR3). Route uses integer path conversion and the action allow-list (`indico/modules/rb/blueprint.py:74-78`). | Live route returns 405 for these malformed paths. Status mismatch; the valid target reservation remained unchanged. |
| API-0011–0013, API-0066–0068, API-0240–0242, API-0260–0262 | Empty, `1`, `not-in-enum`, or null `X-Requested-With` values were sent to timeline, multi-room timeline, booking detail, and approve requests. The app returned **200** for each. In API-0260–0262, the approve request changed the shared booking to `accepted`, confirmed by read-back. | The generated cases treat values outside the OpenAPI header enum as invalid (expected 422 on the timeline/action calls; 403 for booking detail due the generator's available-response fallback). | **Test-basis/spec mismatch, not a confirmed app defect.** Source uses this non-standard header to decide whether an error is rendered as JSON; it does not validate the header on successful requests (`indico/web/flask/wrappers.py:94`, `indico/web/errors.py:85`). Keep these results visible until the team decides whether to remove this header from input-validation coverage or change the contract. The role/state checks themselves passed for valid requests. |
| API-0028, API-0083 | Timeline GET and POST omitted `repeat_frequency` while sending valid dates and `repeat_interval=1` -> **500**, body message `Unexpected frequency NEVER`. | The optional field defaults to `NEVER`; a single-date availability lookup should return 200. Source declares `load_default='NEVER'` (`indico/modules/rb/controllers/backend/bookings.py:64-70`); recurrence generation compares with the `RepeatFrequency.NEVER` enum and raises for other values (`indico/modules/rb/models/reservation_occurrences.py:201-230`). | Suspected app defect. **Inference:** the string default may not be normalized to the enum value before recurrence generation. Actual responses and error text are in the transcript. |
| API-0182 | `POST /rooms/api/booking/create` with `user: null` and all other fields valid -> **422**, `webargs_errors.user = "Field may not be null."` | The current OpenAPI request schema marks `user` nullable and the generated case expects 200. The omitted field already means the authenticated user (`indico/modules/rb/schemas.py:417`; create default in `indico/modules/rb/controllers/backend/bookings.py:201`). | Contract/test-basis mismatch. Decide whether explicit null should mean “no booked-for override” or should be disallowed in OpenAPI. The rejection left the shared reservation unchanged. |
| API-0184 | Same create request with `user: 1` -> **500**, JSON error message `AttributeError: 'int' object has no attribute 'split'`. | A non-string principal identifier should be rejected as a client validation error (422), not trigger a server error. `CreateBookingSchema` uses `Principal` (`indico/modules/rb/schemas.py:417`); principal parsing calls `identifier.split` and the field only converts `ValueError` to a validation error (`indico/util/user.py:60-83`; `indico/util/marshmallow.py:341-359`). | Suspected input-validation defect. The shared reservation remained unchanged. |
| API-0186, API-0188 | Create with `reason: ""` and with `reason` omitted -> **422**, `Booking reason not specified`. | OpenAPI/cases treat `reason` as optional and empty as a valid partition; expected 200. | Configuration-dependent contract mismatch. Indico's seeded/default Room Booking setting is `booking_reason_required=always` (`indico/modules/rb/__init__.py:64`), enforced in `CreateBookingSchema` (`indico/modules/rb/schemas.py:438-449`). This is expected for the current configuration, not evidence of a general app defect. Keep the test basis explicit about this room setting. |
| API-0281–0282 | `POST /rooms/api/bookings/92/reject` (and `/93/reject`) with JSON `{"reason":""}` -> **500**, `There was a database error while processing your request.` | Empty reject reason should be rejected as 422; BR3_REJECT requires a reason to be present and non-empty. The endpoint requires a string but declares no non-empty validator (`indico/modules/rb/controllers/backend/bookings.py:270-279`); the occurrence model has a database check constraint against an empty rejection reason (`indico/modules/rb/models/reservation_occurrences.py:70`). | Suspected app defect: validate non-empty reason before writing so invalid input does not become a 500. The reservation read-back stayed unchanged. |
| Repeated request; rapid concurrent request | The identical create payload sent twice sequentially returned **200** with booking IDs **161** and **162**. Two concurrent identical requests returned **200** with IDs **163** and **164**. Each returned reservation was read back successfully as a separate pending record. | The task prompt requires repeated identical requests to leave no duplicate records. | Observed duplicate creation. **Test-basis assumption:** no upstream idempotency/duplicate-prevention rule was found in the inspected source or API contract. The Area 2 requirement is explicit, so the assertions remain and the team should confirm whether idempotency is an intended product rule. |

## Passing coverage from the same run

- All **80/80** generated decision-table combinations passed.
- All **9/9** explicit allowed/disallowed state-transition cases passed, including unchanged-state checks for disallowed transitions.
- The cross-workflow read/update/read test and both lower-role denial tests passed.
- The focused recurrence/date/direct-booking builder check passed **6/6** cases before the final run. It is not included in the 378-test full-suite total.

## Review notes

- The failures above are not being hidden by changing generated expected statuses or by weakening assertions.
- The OpenAPI-derived assumptions that need team review are explicit-null `user`, optional/empty create reason under the selected room configuration, invalid values for the error-format header, and duplicate-create prevention.
- No application source or upstream test files were changed.
